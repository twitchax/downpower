# PRD-0004 log

## T-001 -- 2026-11-18

**The spike.** `crates/downpower-server/examples/search_spike.rs` builds the event set from the
local raw store (22,428 events once the weekend pages are in, 35 MB of lowercased title, text,
site or licensee names and persons), writes it in batches of 500 to a scratch SurrealDB opened as
`db::open` opens the real one (64 MiB block cache and memtable), and times eight queries five times
each against a `FULLTEXT ANALYZER ... BM25` index (`blank,class,punct` tokenizers, `lowercase,ascii`
filters) and against a substring scan of the same text in memory. `VmHWM` is reset before the
write, so the peak is the write's. `SPIKE_NO_INDEX=1` writes the rows without the index.

| On the home box | Index, one core | No index, one core | Index, 128 cores | No index, 128 cores |
|---|---|---|---|---|
| Write | 15.2 s | 0.3 s | 8.3 s | 0.3 s |
| RSS added (peak) | 171 MB (174) | 54 MB | 268 MB (268) | 57 MB |
| On disk | 145 MB | 67 MB | 159 MB | 67 MB |

| Query, one core | Index | Hits | Scan | Hits |
|---|---|---|---|---|
| scram | 13.4 ms | 894 | 10.9 ms | 928 |
| tritium | 14.1 ms | 681 | 16.9 ms | 681 |
| diesel generator | 33.7 ms | 1,119 | 14.2 ms | 1,462 |
| feedwater pump | 16.4 ms | 791 | 11.4 ms | 1,070 |
| fitness for duty | 16.2 ms | 841 | 10.7 ms | 841 |
| turbine trip | 17.1 ms | 907 | 16.9 ms | 980 |
| palo verde | 6.1 ms | 286 | 11.0 ms | 286 |
| overexposure | 7.0 ms | 360 | 15.8 ms | 562 |

- **Memory.** The index costs about 117 MB more than the same rows without it on one core, and
  211 MB on 128. The Fly VM's peak is 511 MB already (PRD-0003.log.md#t-011-2026-11-18), so it
  would fit under 1 GB, with 280 MB or less to spare.
- **Speed.** Both answer in tens of milliseconds on one core. The scan holds 35 MB per build
  (twice that while a rebuild swaps) and needs no index work on a rebuild or update.
- **Matching.** The index matches whole tokens: `scram` misses "scrammed", and `overexposure`
  misses "overexposures". The scan matches substrings, closer to what a filter box implies.
- **Not measured on the Fly VM.** The spike needs the raw store and a release build there; the
  scan's latency on the shared CPU is measured with the explorer's deploy (T-008).

**The choice, Aaron's, 2026-11-18: the scan.** The index would fit, but it buys no speed for its
memory and write time, and the scan's substring matching suits a filter box. Decision 34 is
revised to match.

## T-004 -- 2026-11-18

**The palette.** The counts chart's eight series take the cause families' hues in the families'
own order (`style/_series.scss`), so every neighboring pair keeps the colorblind and normal-vision
separation `_families.scss` records for both chart surfaces, and Other takes Unattributed's gray.
The explorer is its own page, so a hue never stands for a family and a category at once. The
category toggles carry each group's swatch and label, the readout names every series, and the list
under the chart holds every event, so no count rests on color alone.

**The geometry.** `area::stack_series` and `area::peak_series` take any keyed series, and the home
page's `stack` and `peak` call them with the families.

## T-005 -- 2026-11-18

**The NRC link.** A page date isn't recoverable from an event's own dates: EN 46556 (event
2011-01-19, notified 01-20) sits on the 2011-01-19 page, while EN 58149 (event 2026-01-12) sits on
the 2026-02-11 page. So the event set keeps the date of the page each event came from, and the
build stores it with the event (`StoredEvent::page`, in the event's hash, so the next update writes
it to every event once).

**Client-side, like the rest.** The event page loads `/api/events/{number}` in the browser, as the
home page and `/status` load theirs, so the server sends the same shell for every number. uat-005's
404 for an unknown number is the API's; the page then reads "No event N".

## T-006 -- 2026-11-18

**The buffer.** `/api/markers` packs each unit of every unretracted reactor event (the build's
event unit rows) as a docket index, a day from 1999-01-01, a scram flag and the event number: 9
bytes a marker behind a table of dockets, so the markers don't depend on the barcode's row order.
It carries a weak `ETag` from its bytes and is cached per build.

**The drawing.** With `events=1` the barcode draws each marked cell over its colors in the text
color: a one-pixel tick the row's height for an event, a diamond for a scram, so they read apart by
shape (Decision 35). Several events on one cell draw once, a scram winning. The legend's `Events`
toggle carries the diamond as its key.

**Hover and click.** The readout names the events on the hovered unit and days, a scram first, and
a click or Enter opens the first. It doesn't show titles: that would take a request per hover on top
of the unit-day's, and the event page is one click away.
