# Summary
The NRC's Event Notification Reports, parsed in full and joined to the status-report ledger. Every
event of every category since 1999 becomes an `event` row with its update timeline, reactor events
map to units, the ledger's `See EN#` days take their cause from the event they point to, and two
scram checks measure how well the two NRC sources agree. The explorer (PRD-0004) and the FFD view
(PRD-0005) build on this.

# Problem
The status reports point to events for 58 TWh of lost output (2.4% of the archive, half of
Unattributed) with a bare `See EN# N`, and the ledger can't say what happened on those days. The
7,271 event pages are already in the raw store (PRD-0002 T-002), but nothing parses them: the
categories beyond Power Reactor, the appended updates and retractions, and the facility names that
change case and spelling over 27 years all need handling before any view can trust them.

# Goals
1. Every stored event parses into one `event` row, under both header templates, with its 10 CFR
   sections, unit table, persons, text and update timeline.
2. Reactor events map to dockets, fuel cycle and research reactor events to catalogued facilities,
   and materials events to (state, license number) groups.
3. `See EN#` days resolve to a cause with method `xref_en_v1` and evidence.
4. Event pages settle at 28 days, and a late status report is picked up on the next run.
5. `/status` shows how much of the archive parsed, what the catalogs didn't know, and both scram
   agreement rates.

# Technical Approach

```text
 nrc.gov EN pages ──┐                                        catalog/ (committed)
 nrc.gov status ────┼─▶ raw store ─▶ events::parse ─▶ event set ─▶ identity ─▶ Surreal: event, event_unit
 scram dataset.xlsx ┘   (Decision 15)  per page        newest     units.csv          │
                                                       fetch wins  facilities.csv     ▼
                                     status::parse ─▶ observe ─▶ attribute ◀── xref.toml (xref_en_v1)
                                                                      │
                                                                      ▼
                                                                  unit_day ─▶ scram checks ─▶ /status
```

- **Where the code goes.** `downpower-ingest` gets `events` (the page parser and the update
  timeline), `facilities` (the identity catalogs), `xref` (the rule table), and `scrams` (both
  checks). It stays free of Surreal. `downpower-server` writes the event tables and serves the
  `/status` additions. The scram dataset is a new `raw::Series`, fetched like `NUC_STATUS`.
- **Parsing.** Each event is a `<div class="grid border" id="enNNNNN">` of `<b>Label:</b> value`
  pairs, then the unit table (reactor categories), then the text. Like `status::parse`, it builds a
  DOM of `<main>` alone, not the whole page (PRD-0002 T-019). The parser knows every label and fails
  on a new one, the way the status parser fails on a new column set. NUL placeholders become empty.
- **One build.** A rebuild parses every EN page first, then the status pages, so attribution can
  resolve references against the event set. Events live in `event_<n>`, numbered as the build's
  `unit_day_<n>` and swapped and dropped with it; `ledger:current` records the archive's counts. The in-place update (Decision 15) hashes each event
  and rewrites only changed ones, as `chunks` does for unit-months.
- **Resolution.** `catalog/xref.toml` is an ordered rule list. Each rule matches a scram code or a
  10 CFR code prefix and names a fine cause from `catalog/tags.toml` (`scram`, a new
  `required_shutdown`, and the fallback `en_reported`, both Forced). Evidence is the event number
  and the field that decided. A reference resolves only to a non-retracted event on the same
  docket; the rest stay `xref_unresolved` with the reason.
- **Fetching.** `Report::EventNotifications.hold()` becomes 28 days. Each run takes the newest
  week of EN pages, the page that has just passed its hold, and catches up unsettled pages, as for
  status pages. A status date inside its hold whose stored page reads "No data available" is
  fetched again on every run until a report appears.
- **The scram checks.** Internally, an EN scram (unit scram code other than `N`) should meet a
  drop to zero, or a `scram` cause, on that unit within a day, and a status-report scram outage
  should meet an EN within two days. Externally, the NRC dataset reconciles by (event number,
  docket) from 2011 to 2025-03. `cargo xtask scrams` prints the disagreements, and `/status`
  shows the rates.

# Assumptions
- 639 of 7,271 stored pages read "No events found", and the event numbers have gaps (35211 to
  58530 is 23,320 numbers for 19,725 events). Both are counted and reported, not failed on. The
  empty pages are no proxy for holidays: 1999 has 6 against its 10 weekday holidays
  (PRD-0003.log.md#t-001).
- A reference whose event is on another unit or in another category is a typo or a shared-site
  event; it stays unresolved and is counted, not guessed.
- An update's date is reliable enough to sort the timeline (96.7% plausible); the from and to
  names are for display only.
- The NRC's raw data file and the scram dataset are US government works, so committing small
  fixtures from them is allowed (data.gov lists both as CC0).

# Constraints
- nrc.gov gets at most one request every 5 s under the declared User-Agent, and a 403 stops the
  run (Decision 10).
- The rebuild has to fit the 1 GB Fly VM next to the serving build: about 20,000 events of text
  add tens of MB.
- No new chart or component library. The xlsx parser (`calamine`, MIT) is the one new dependency.
- Stable toolchain 1.99.
