## T-003 -- 2026-11-16

Every build now holds the event set beside its ledger.

- **Shape.** `EventSet::build` parses the newest capture of each stored event page and keeps one
  copy per event: the one from the page fetched last, and between pages fetched at the same moment,
  the later date. The server writes it to `event_<n>`, numbered as the build's `unit_day_<n>`, one
  record per event under its number. The build record carries an `Archive` (pages, empty pages,
  events, failed dates), and `LEDGER_VERSION` is 4, so the next deploy rebuilds.
- **Order.** The writer builds the event set before the status pages, so T-005 can resolve `See EN#`
  against it inside the same build.
- **Updates.** Each event is hashed with the unit-months' FNV-1a (`chunks::hash`, now generic, with
  the same bytes for days as before), and the hashes are stored in `chunks:[event_<n>]`. An update
  rewrites only the events whose hash moved (a delete and an insert in one transaction) and deletes
  those no page holds any longer. `refresh` updates in place only when both sets of hashes exist.
- **Failures.** A page that doesn't parse fails `downpower rebuild` and the backfill, naming the
  page, and is skipped and counted (`Archive::failed`) by the server's refresh, as Decision 21 does
  for unknown names. A new label on one NRC page can't freeze the site's updates.
- **`event_unit` moved to T-004.** It exists to find events by docket (PRD-0004's markers, T-007's
  scram check), and dockets come from T-004's facility identity. Until then each event row carries
  its unit table.
- **Dropping.** An old build's event table goes with one `REMOVE TABLE`: about 35 MB of events,
  against the unit-day table that still needs deleting a unit at a time.

Measured on the home box, release build, pinned to one core (as T-019 did), over the full raw store
(7,271 event pages, 10,179 status pages):

| Run | Wall | Peak RSS |
|---|---|---|
| Full rebuild into an empty database | 43.8 s | 320 MB |
| Full rebuild over a previous build (drops it) | 71.8 s | 412 MB |

- 19,725 events and 1,016,840 unit-days per build. In the second run, deleting the old unit-day
  table took about 26 s; removing the old event table took under a second.
- T-019 measured 73 s for the same one-core rebuild before events, so the event set adds little
  time (parsing every event page is about 3 s). Its memory share isn't separated here: `cargo
  xtask events`, holding every copy of every event, peaks at 99 MB, an upper bound. T-011 measures
  the real thing on Fly.

## T-005 -- 2026-11-17

- **Resolution.** A `See EN# N` resolves when the event set holds N, its unit table lists the
  day's unit, and the event isn't retracted. Otherwise it stays `xref_unresolved` with the reason
  (`no_number`, `missing`, `other_unit`, `retracted`, checked in that order), and a non-reactor
  event counts as `other_unit`. No date window is applied: every resolved reference cites an
  event from the same day to no more than a year before it.
- **Rules** (`catalog/xref.toml`). A SCRAM Code of `A/R`, `M/R`, `A` or `M` gives `scram`;
  `PLANT S/D REQD BY TS` under 50.72(b)(2)(i) or the older (b)(1)(i)(A) gives
  `required_shutdown`; anything else falls back to `en_reported`. Both new causes are Forced.
  - **One code, two meanings.** The 2000 revision of 10 CFR 50.72 moved the required shutdown to
    (b)(2)(i), which had been the 4-hour degraded or unanalyzed condition. The archive carries 306
    reactor events with (b)(2)(i) `PLANT S/D REQD BY TS` and 67 with (b)(2)(i)
    `DEG/UNANALYZED COND`, and both appear in 2001 (the new meaning from EN 37677 on 2001-01-23,
    the old one until EN 38444 on 2001-10-30). So the section rule matches the description too.
  - **No RPS rule.** `RPS ACTUATION - CRITICAL` belongs to the event, and on a multi-unit event
    names only the unit that scrammed (EN 54794: Browns Ferry 2 scrammed, 1 and 3 reduced
    power). The unit's SCRAM Code decides instead. Five resolved days cite an event with that
    section and code `N`; three resolve to `required_shutdown` through the event's other section
    and two to `en_reported`, Forced either way.
- **Precedence.** A resolved cause competes with the reason's own causes and loses a tie to them,
  since those are observed. A resolved day starts an inheritance chain like any attributed day.

## T-007 -- 2026-11-17

**The check.** `downpower_ingest::scrams::Check` runs inside every build beside the ledger; its
counts go into the build summary, `/api/status` and `/status`, and `cargo xtask scrams` prints them
with the disagreements. A retracted event counts toward neither direction (Decision 30).

- An **EN scram** is a unit a live event's table gives a SCRAM Code other than `N`. It is
  `dropped` when an NRC row the day of the event or the next reads 10 or more points below its
  initial power, else `named` when such a row carries the Scrams (#) count, a `scram` tag or a
  citation of the event, else `no_report` (no NRC row either day), `low_power` (from under 10%,
  which can't show a drop) or `missed`. The agreement rate is dropped and named of those plus
  missed.
- A **report scram** is the first of a run of consecutive NRC rows carrying the Scrams (#) count
  or a `scram` tag, dated by its Down date when that falls within the 7 days before. It is
  `event` when a live event on the unit within 2 days, or one its reason cites, gives a SCRAM Code
  other than `N`; else `retracted` when only a retracted one does, `no_scram_code` when events on
  the unit are near but none scrams it, and `missed`. The agreement rate is event of event,
  no_scram_code and missed.
