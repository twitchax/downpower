  event time zone.
- 62 events have no title. The sampled ones open on a `* * *` line: the 2004–2007 re-postings that

## T-002 -- 2026-11-16

`Event::updates` splits the text at its markers, and `Event::revised` reads the revision header.
Over the archive (`cargo xtask events`, all 7,271 pages, no failures):

- 6,145 markers: Update 4,897, Retraction 1,215, PartialRetraction 4, Unretraction 3, and 26 notes
  (Commissioners' assistants' briefings, `HOO NOTE`s, summaries, closeouts). 4,986 events carry
  any: 4,290 one, 515 two, 181 three or more. 1,201 events carry a revision header.
- Of the 6,119 update and retraction markers, the date parses on 99.3%, the time on 98.0%, and
  both names on 95.3%. The Python survey's regexes reached 97.3%, 94.0% and 94.4%. The gains come
  from typos of the keyword (`UDATE`, `UDPATE`, `UPDATEON`), five markers missing their opening
  stars, spelled dates (`MAY 28, 2021`, `14 APRIL 2021`, common since about 2018), and `12:42`.
  Taking a spelled date out before reading the time also stops `2021` reading as 20:21.
- What stays unparsed: markers with no date written (`UPDATE 1608 ET FROM T. HUFF TO M. RIPLEY`)
  and typos (`17/14/05`, `9/5/203`, `1//19/2015`, `1/17/18/17`). 59 parsed dates (1.0%) fall
  outside the day before notification to the day after the last update.
- Kinds come from a keyword anywhere in the marker, so `SEE EN #50998 FOR CONTINUATION OF
  UPDATES` reads as an update. The kind is for display; nothing counts by it.

**The banner decides retraction.** Against the page's `THIS EVENT HAS BEEN RETRACTED` banner:

| Banner | Retraction marker | Events |
|---|---|---|
| yes | yes | 1,176 |
| yes | no | 271 |
| no | yes | 38 |
| no | no | 18,240 |

- The 271 banner events without a retraction marker retract inside an `UPDATE`'s text.
- The 38 markers without a banner are mostly retractions withdrawn later. Some say so in a plain
  `UPDATE` ("the retraction made on June 6, 2005 is being cancelled", EN 41725; EN 37330, 38704),
  and three are `UNRETRACTION`s. A few look like retractions the NRC never flagged (EN 44236,
  48018).
- Wording is worse than markers. Of 87 events whose text after a marker says "retract" with no
  banner, the samples are partial retractions (one criterion withdrawn, another standing),
  retracted Alert classifications, and radiography sources "retracted into the camera" (EN
  41695).
- So `Event::retracted` stays the banner, the NRC's own flag, which the scram dataset's
  `NRC_retract_flag` presumably shares (T-008 will tell). Retraction markers are timeline entries.
  DESIGN.md Decision 30 records this.

**Escaped line breaks.** Nine revision headers from December 2025 (EN 57883 to 58078) carry their
line breaks escaped, as `&lt;br&gt;`, so the page shows `12/11/2025<br><br>EN Revision Text: ...`
on one line. The strict revision-date parse failed seven pages on them, and `event_text` now reads
an escaped `<br>` as a line break. Nothing else in the archive is escaped markup.

**A parser per run.** `events::Parser` compiles the selectors and the four marker patterns once,
and `cargo xtask events` reuses one across the archive. `events::parse` stays for one-off use.

## T-003 -- 2026-11-16

Every build now holds the event set beside its ledger.

- **Shape.** `EventSet::build` parses the newest capture of each stored event page and keeps one
  copy per event: the one from the page fetched last, and between pages fetched at the same moment,
  the later date. The server writes it to `event_<n>`, numbered as the build's `unit_day_<n>`, one
  record per event under its number. The build record carries an `Archive` (pages, empty pages,
  events, failed dates), and `LEDGER_VERSION` is 4, so the next deploy rebuilds.
- **Order.** The writer builds the event set before the status pages, so T-005 can resolve `See EN#`
  against it inside the same build.
- **Updates.** Each event is hashed with the unit-months' FNV-1a (`chunks::hash`, now generic, with
  the same bytes for days as before), and the hashes are stored in `chunks:[event_<n>]`. An update
  rewrites only the events whose hash moved (a delete and an insert in one transaction) and deletes
  those no page holds any longer. `refresh` updates in place only when both sets of hashes exist.
- **Failures.** A page that doesn't parse fails `downpower rebuild` and the backfill, naming the
  page, and is skipped and counted (`Archive::failed`) by the server's refresh, as Decision 21 does
  for unknown names. A new label on one NRC page can't freeze the site's updates.
- **`event_unit` moved to T-004.** It exists to find events by docket (PRD-0004's markers, T-007's
  scram check), and dockets come from T-004's facility identity. Until then each event row carries
  its unit table.
- **Dropping.** An old build's event table goes with one `REMOVE TABLE`: about 35 MB of events,
  against the unit-day table that still needs deleting a unit at a time.

Measured on the home box, release build, pinned to one core (as T-019 did), over the full raw store
(7,271 event pages, 10,179 status pages):

| Run | Wall | Peak RSS |
|---|---|---|
| Full rebuild into an empty database | 43.8 s | 320 MB |
| Full rebuild over a previous build (drops it) | 71.8 s | 412 MB |

- 19,725 events and 1,016,840 unit-days per build. In the second run, deleting the old unit-day
  table took about 26 s; removing the old event table took under a second.
- T-019 measured 73 s for the same one-core rebuild before events, so the event set adds little
  time (parsing every event page is about 3 s). Its memory share isn't separated here: `cargo
  xtask events`, holding every copy of every event, peaks at 99 MB, an upper bound. T-011 measures
  the real thing on Fly.

## T-004 -- 2026-11-16

Every event in a build now says who it is about (`downpower_ingest::facilities`).

- **Reactors.** Power Reactor events name a site and unit numbers (`PALO VERDE`, units 1 to 3),
  never a unit's own name. `catalog/units.csv` gains `en_site` (every EN spelling of the unit's
  site, `;`-joined) and `en_unit`, and `catalog/facilities.csv` lists the 19 units outside the
  ledger the same way: Bellefonte 1 and 2, Big Rock Point, Dresden 1, Haddam Neck, Humboldt Bay 3,
  La Crosse, Maine Yankee, Millstone 1, North Anna 3, Rancho Seco, San Onofre 1, Summer 2 and 3,
  Three Mile Island 2, Trojan, Yankee Rowe, Zion 1 and 2. Names match ignoring case and runs of
  spaces; the spellings that need a listing of their own are `Cook`, `Davis Besse`, `Harris`,
  `LaSalle`, `Ft Calhoun`, `Washington Nuclear`, `WNP-2`, `Vogtle 1/2`, `Vogtle 3/4` and
  `Summer Construction`. Five events name a site with an empty unit table, and map to no unit.
- **Fuel cycle facilities** (18) match on (state, name): `GENERAL ELECTRIC CO.` is GE Morris
  (72-1) in IL and GE Vallecitos (70-754) in CA. Each facility lists its names under every owner
  (Allied-Signal then Honeywell; Siemens, Framatome ANP, AREVA at Richland; CE then Westinghouse at
  Hematite; B&W Nuclear Operating Group and BWX Technologies at Lynchburg). Two are not Part 70
  plants: Mallinckrodt's Mo-99 generator line (Part 30, 030-00001) and Fort St. Vrain's ISFSI
  (72-9).
- **Non-power reactors** (32) match on license number. The pages print each docket beside its
  license, which is the source for those rows, except `0500123`, printed under both R-79 (Missouri
  S&T, 50-123) and R-103 (University of Missouri, 50-186).
- **Licensees** group by (state, license number) as letters and digits in upper case, under the
  name on the group's highest-numbered event that has one. A license with no digit (`GL`, `N/A`,
  `General License`, `Confidential - NY Medical Licensee`) is a placeholder, and the event stays
  text, as do Part 21 vendors and the 35 licensee events with no state.

  | Key | Groups |
  |---|---|
  | License as printed | 4,828 |
  | Spaces removed, upper case | 4,764 |
  | Letters and digits only | 4,631 |

  Dropping punctuation merges 126 more groups; the 40 read were each one license written two
  ways (`21-01190.05` and `21-01190-05`, `L-02187` and `L02187`). Dropping leading zeros too would
  merge 8 more, and isn't done. 780 groups carry more than one name.
- **Coverage.** All 19,725 events: 9,830 reactor events by unit, 5 by site, 1,066 at a catalogued
  facility, 7,107 by licensee, and 1,717 text. No name is unknown, and every catalog spelling is
  used (`uat_event_identity_knows_every_facility_the_archive_names_and_uses_every_catalog_name`,
  over a fixture of the 351 facility keys the archive holds).
- **Sources.** Each `facilities.csv` row names one. nrc.gov answered the first request (its list of
  power reactor sites undergoing decommissioning: Dresden 1, Millstone 1, San Onofre 1, TMI 2) and
  refused the second with a 403, so the rest come from Federal Register notices on govinfo.gov.
  What the sources leave inferred:
  - Bellefonte 2 is 50-439 by elimination; Summer 2 and 3 and Zion 1 and 2 by the order the
    notices list them in.
  - Global Laser Enrichment's 2024 event (EN 57394) is mapped to GNF-A Wilmington (70-1113), since
    a 2024 notice says the GLE test loop runs under GNF-A's license SNM-1097. GLE's own docket,
    70-7033, belongs to the Paducah laser enrichment application.
  - Battelle's High Energy Cell events (2001–2004) are mapped to its West Jefferson license
    SNM-7 (70-8). The notice places the site; the cell's tie to that license is from inspection
    report snippets.
- **Storage.** Each stored event carries its `identity` (`reactor` with dockets, `facility` with
  docket and catalog name, or `licensee` with state, license and the group's newest name).
  `event_unit_<n>` holds one row per unit of a mapped reactor event, keyed `[number, unit]`, with
  the docket, the day it happened, the scram code and the retraction flag, for PRD-0004's markers
  and T-007's scram check. An event's hash covers its identity, so a renamed group rewrites its
  events in place. `LEDGER_VERSION` is 5, and `catalog/facilities.csv` joins the derived version.

| Full rebuild into an empty database | 43.9 s | 325 MB |
| Full rebuild over a previous build (drops it) | 74.8 s | 418 MB |
